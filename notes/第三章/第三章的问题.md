### 用迷你语料库计算 agent works 的 Bigram 概率

语料库：

```python
datawhale agent learns
datawhale agent works
```

把所有的词写出来：

```py
datawhale
agent
learns
datawhale
agent
works
```

总共6个词，Datawhale 在正文的 Bigram 计算方式是：$P(w_1,w_2,\cdots,w_n) \approx P(w_1) \prod_{i=2}^{n}P(w_i|w_{i-1})$

并使用最大似然估计：$P(w_i|w_{i-1}) = \frac{Count(w_{i-1},w_i)} {Count(w_{i-1})}$

**第一步：计算P(agent)**

`agent`出现了2次，总次数为6:        $p(agent) = \frac {2} {6} = \frac {1}{3}$

**第二步： 计算P(works|agent)**

语料中：

```
agent learns
agent works
```

`agent`后面一共出现过两个词：

- learns ： 1次
- works : 1次

所以：$P(works|agent) = \frac{Count(agent,works)} {Count(agent)} = \frac12$

因此：$ P(agent\ works) = P(agent)\times P(works|agent) = \frac13\times\frac12 = \frac16 \approx0.167 $

还有一个细节值得注意：如果采用更严格的语言模型写法，给句子加入 `<s> <\s>`,那么`agent` 从来没有作为句首出现：

```python
<s> datawhale agent learns </s>
<s> datawhale agent works </s>
```

此时 : $P(agent|<s>)=0$ , 导致整个句子的概率会变成0

### 什么是 N - gram 的马尔可夫假设 ？

真正的语言概率应该写成：$P(w_1,w_2,\cdots,w_n) = P(w_1) P(w_2|w_1) P(w_3|w_1,w_2) \cdots$

也就是说，预测第 i 个词时: $P(w_i|w_1,w_2,\cdots,w_{i-1})$,理论上应该考虑前面的**所有历史信息**

那么问题来了。假设现在有一句：The agent that Datawhale developed last year works well.当预测 `agent`时，你理论上可能需要知道很前面的 `agent`,但是统计语言模型没法统计所有可能的长句组合，因为组合数量会爆炸，于是引入：**马尔可夫假设 ： 未来主要由有限长度的最近历史决定** 。 

对于 Bigram : $P(w_i|w_1,\cdots,w_{i-1}) \approx P(w_i|w_{i-1})$ , 只看前面 1 个词

对于 Trigram : $ P(w_i|w_1,\cdots,w_{i-1}) \approx P(w_i|w_{i-2},w_{i-1})$  只看前面2个词

所以 N-gram 的本质就是：

```
完整历史
↓↓↓ 强行截断
最近 N-1 个词
↓↓↓
预测下一个词
```

这是一种工程上的妥协。

### N - gram 有哪些根本局限？

最重要的有四个：

| 局限             | 本质                                    |
| ---------------- | --------------------------------------- |
| 数据稀疏         | 没出现过的词组合概率直接变 0            |
| 无法理解语义     | `agent` 和 `robot` 是完全不同的离散符号 |
| 固定上下文       | 只能看前 \(N-1\) 个词                   |
| N 增大后组合爆炸 | N 越大，需要统计的组合数量指数增长      |

Datawhale 特别强调了前两点： **数据稀疏性和泛化能力差**，比如模型见过很多次`agent learns` ,并不会因此知道 `robot learns` 也很合理，这就是后来 **Embedding** 出现的重要原因。

### RNN / LSTM 怎么克服 N - gram ?

先看最关键的改变

N - gram :

```python
w1 w2 w3 w4 w5
         ↑
只保存固定几个词
```

RNN:

```python
w1 → h1
      ↓
w2 → h2
      ↓
w3 → h3
      ↓
w4 → h4
```

其中:     $  h_t=f(x_t,h_{t-1})$    $h_t$ 是隐藏状态

可以理解为 **读到当前词以后，对目前为止所有信息做出来的一份压缩笔记**

比如：

```
The agent developed by Datawhale last year works
```

处理过程：

```
The
 ↓
h1

agent + h1
 ↓
h2

developed + h2
 ↓
h3

...

works + h7
```

理论上 `works` 能够通过隐藏状态获得很早之前的 `agent` 信息，所以 RNN 打破了 N - gram : 只能看固定 N-1 个词 这个限制。

**但普通 RNN 又出了一个问题**：

信息传递路径太长，例如：

```
agent → → → → → → → → → works
```

训练时梯度必须：

```
works
 ← ← ← ← ← ← ←
agent
```

反向传播很多次，就容易出现梯度消失，梯度爆炸等，于是模型还是会忘记很久之前的信息。

**LSTM怎么解决 ？**

LSTM 在 RNN 里面又增加了一条：叫做 **Cell State , 细胞状态**。可以理解成一条专门的长期信息高速公路，再搭配三个门：

-  **遗忘门：** 决定以前的信息哪些不要了
- **输入门：** 决定当前信息哪些值得记住
- **输出门：** 决定当前应该拿哪些记忆出来使用

于是：

```
普通 RNN

h1 → h2 → h3 → h4 → h5


LSTM

C1 =======================→ C5
 ↓       ↓       ↓          ↓
h1 →    h2 →    h3 →       h5
```

长距离信息更容易保存，Datawhale 也正是从长期依赖和三个门来解释 LSTM

### Transformer 又怎么克服 RNN / LSTM ?

RNN 最大的问题变成了: **必须一个词一个词往后算**，因为 $h_t$ 依赖 $h_{t-1}$ 所以：

```
w1
 ↓
w2
 ↓
w3
 ↓
w4
 ↓
w5
```

没办法跳，而 Transformer 做了一件很强的事情 ：**把循环结构整个删掉** 变成 Self - Attention :

```
       ┌───────────────┐
       ↓               │
agent  Datawhale  ... works
 ↑       ↑        ↑     ↑
 └────所有 token 相互看────┘
```

`works` 想找 `agent` 直接算 $Q_{works}K^T_{agent}$ ,不用经过：

```
h3 → h4 → h5 → h6
```

这使长距离依赖从：“经过很多时间步传递” 变成 “一次 Attention” 直接建立联系。同时所有 token 可以进行大规模矩阵并行计算。Transformer 因此比 RNN 更适合 GPU 和 大规模训练。

可以把三代模型记成：

```
N-gram
记最近几个词
    ↓
RNN/LSTM
把历史压缩进记忆
    ↓
Transformer
所有 token 直接建立联系
```

### Self - Attention 的核心思想到底是什么？

**一个 token 在形成自己的新表示时，根据当前任务，动态决定应该从其他 token 身上拿多少信息** 

**为什么需要 Q , K , V ?**

假设有：

```
The agent learns
```

每一个 Token 原来是一个 embedding ：$ x_i\in R^{d_{model}} $

通过三个线性层：

​					$Q=XW_Q $

​					$ K=XW_K $

​					$ V=XW_V $

分别扮演：

- Q : 我现在想找什么？
- K : 我有什么特征供你匹配？
- V : 如果你关注我，我真正给你什么信息

计算： $QK^T$  ,也就是 每个 token 和所有 token 的相关程度。

再： $\frac {QK^T}{\sqrt{d_k}}$  -> Softmax : $A = Softmax(\frac{QK^T}{\sqrt{d_k}})$  -> AV

也就是 ： 按注意力权重对所有 V 加权求和

再用具体的维度完整推一遍：

假设 B = 32 , L = 100 , $d_{model}$  = 512 , 输入 ： X [32,100,512]

经过 $W_Q, W_k , W_V$ :

```
Q [32,100,512]
K [32,100,512]
V [32,100,512]
```

假设 h= 8 , 那么 $d_k = \frac {512}8 = 64$ ,然后拆头：

  ```
  Q [32,8,100,64]
  K [32,8,100,64]
  V [32,8,100,64]
  ```

计算：$QK^T$

得到 ：

``` 
[32,8,100,100]
```

这里的两个 100 就是 

```
每个 Query token
      ×
所有 Key token
```

所以 Attention Matrix 本质就是 ： 一个 token 和另一个 token 之间该关注多少的表格

最后：

```
Attention × V

[32,8,100,100]
×
[32,8,100,64]
                       拼接8个头
→ [32,8,100,64]           ->     [32,100,512] 
```

于是输入输出维度重新回到 ： $d_{model} = 512$  ,这就是 $h × d_k = d_{model}$ 在标准实现中的来源。

### 为什么 Transformer 可以并行，而 RNN 不行？

这是一个非常本质的问题。

**RNN** :	$h_t = f(x_t,h_{t-1})$   所以 $h_3$ 必须等 $h_2$ ,而$h_2 又要等 h_1$ ,因此：

```
x1 → h1
       ↓
x2 → h2
       ↓
x3 → h3
       ↓
x4 → h4
像排队过独木桥
```

**Transformer** ： Transformer 没有 ： $h_t ← h_{t-1}$ 这样的依赖

直接把： X = [$x_1,x_2,x_3,x_4$] ,一次性送进去：

$Q = XW_Q$

$K = XW_K$

$V=XW_V$

全都是矩阵乘法，于是 GPU 可以同时计算所有 token ，这正是 Transformer 训练速度和可拓展性的重要来源。

### 那并行之后，模型怎么知道词序？

RNN 天然有：

```
先 x1
再 x2
再 x3
```

所以顺序天然存在，Transformer 一次：

```
[x1,x2,x3,x4]
```

一起处理，所以 Self - Attention 本身并不知道 ：`agent learns` 和 `learns  agent` 谁先谁后，于是加入 **Positional Encoding （位置编码）** ，输入不再只有 $Embedding(token)$ ,而是 $Input = TokenEmbedding + PositionEmbedding$ ,比如：

```
agent 在第0位：

agent_embedding + PE(0)

agent 在第5位：

agent_embedding + PE(5)
```

同一个 `agent` 词向量一样 + 位置向量不同 = 最终表示不同

原始 Transformer 使用正弦余弦：

$PE(pos,2i) = \sin \left( \frac{pos}{10000^{2i/d_{model}}} \right)$ 

 $PE(pos,2i+1) = \cos \left( \frac{pos}{10000^{2i/d_{model}}} \right)$ 

例如翻译：

```
I love AI
   ↓
Encoder
   ↓
理解英文
   ↓
Decoder
   ↓
我喜欢人工智能
```

Encoder ： 阅读，理解完整输入

Decoder :  根据已经生成的内容 + Encoder 输出生成答案

Decoder 中因此有：

1. Masked Self - Attention
2. Cross - Attention
3. FFN

也就是：

```
Q：来自 Decoder
K：来自 Encoder
V：来自 Encode

## Decoder-Only

GPT 做的事情是：

```text
Encoder
❌ 删除

Decoder
✅ 保留
```

于是：

```
用户问题 + 已生成文本
           ↓
   Masked Self-Attention
           ↓
      预测下一个 token
```

例如：

```
Datawhale Agent is
                    ↓
                    a

Datawhale Agent is a
                      ↓
                      powerful
```

不断 ： $P(x_{t+1}|x_1,\ldots,x_t)$  , 这就是 **Autoregressive 自回归生成**

**为什么训练时不能偷看答案？**

例如训练：

```
I love machine learning
```

训练时四个 token 明明同时存在，但是预测 `machine` 时不能看到后面的 `learn` ,所以加：**Causal Mask** ,Attention Matrix 原来：

```
        I   love machine learning
I       ✓    ✓     ✓       ✓
love    ✓    ✓     ✓       ✓
machine ✓    ✓     ✓       ✓
learning✓    ✓     ✓       ✓
```

变成：

```
        I   love machine learning
I       ✓    ×     ×       ×
love    ✓    ✓     ×       ×
machine ✓    ✓     ✓       ×
learning✓    ✓     ✓       ✓
```

未来位置被 $-\infty$  遮掉，然后经过 Softmax 之后 $e^{-\infty}=0$ ,所以模型无法偷看未来。

### 为什么现代通用 LLM 主要用 Decoder - Only?

严格说不是“所有模型”，而是：**目前通用生成式大语言模型中 Decoder-Only 占据主流**，核心原因有四个：

1. **预训练任务极其统一：**

   只干一件事：预测下一个 Token ，互联网几乎所有文本都可以之间成为训练数据

   ```
   今天 天气 很
              ↓
             好
   ```

   不用人工标注。

2. **输入输出统一成一个序列：**

   回答：

   ```
   Question + Answer
   ```

   翻译：

   ```
   Translate: English → Chinese
   ```

   代码：

   ```
   Instruction + Code
   ```

   Agent:

   ```
   System + User + Tool + Assistant
   ```

   全部都可以变成：

   > 给定前文，预测后文

3. **架构简单，非常适合 Scaling**

   没有：

   ````
   Encoder
   +
   Decoder
   +
   Cross-Attention
   ````

   而是重复堆：

   ```
   Masked Attention
   FFN
   ↓
   Masked Attention
   FFN
   ↓
   ...
   ```

   容易拓展到几十亿，几百亿甚至更大规模

4. **天然适合生成式任务**

   聊天，代码，Agent规划，写作，本质都非常符合：$P(x_{t+1}|x_{≦T})$ 

   因此 Decoder - Only 与现代通用 LLM 任务高度匹配

## 习题3

文本子词分词算法是大语言模型的一项关键技术，负责将文本转换为模型可处理的 token 序列。那为什么不能直接以"字符"或"单词"作为模型的输入单元？BPE（Byte Pair Encoding）算法解决了什么问题？

### 按单词 World-level

比如：

```
I love machine learning
```

切成：

```
["I","love","machine","learning"]
```

看起来非常合理，但是有两个大问题：

**问题一：词表爆炸**

英文：

```
play
plays
played
playing
player
players
```

如果全部当独立 token：

```
play     → 1001
plays    → 2846
played   → 9742
playing  → 5321
...
```

词表会越来越大， Embedding 参数： VbcabSize x d_model 也跟着增加

**问题二：OOV**

突然出现：

```
DatawhaleAgentSuperSystem
```

词表里面没见过，怎么办？以前只能`<UNK>` 直接丢失信息。这叫做 `Out-of-Vocabulary` 未登录词问题。

### 按字符

例如 `agent` 变成 `a` `g` `e` `n` `t` ,优点是 词表特别小，但是问题是原来用 `tokenization` 时只有一个或者几个 token，但是现在生成十几个 token，序列长度暴涨，Self-Attention 的计算量又大致与 $L^2$ 相关，而且单独一个 `t` `o` `k` . . . 语义特别弱，模型还得自己重新学：

```
t+o+k+e+n
=
token
```

效率很低，词表小，没有 OOV , 但是语义粒度太细而且序列更长。

### BPE 做了什么？

BPE 的思想非常漂亮：**常见组合合起来，罕见词继续拆开**。比如：

```
learning
```

可能变成：

```
learn + ing
```

于是模型知道：

```
learn
learning
learned
learner
```

都共享 `learn` 这个部分

**BPE怎么训练？**

初始：

```
h u g
p u g
p u n
b u n
```

统计相邻 token 对，假设：

```
u g
```

出现频率最高，合并：

````
u + g → ug
````

于是：

```
h ug
p ug
p u n
b u n
```

继续统计，再发现：

```
u n
```

很多，于是继续合并：

```
u+n → un
```

于是词表逐渐从‘字符’ 长出 ‘高频字词’，所以说 BPE 找到了中间态

```
字符级
词表小
序列长
语义弱
   ↓
  BPE
   ↑
单词级
词表大
序列短
OOV严重
```

BPE 达成： $\boxed{ 适中的词表 + 适中的序列长度 + 很强的未登录词处理能力 }$

所以 BPE 本质上解决的不是一句：‘怎么把文字切开’，而是在寻找**信息表示粒度的最佳折中**。这点非常重要

代码为：

```python
import torch
from transformers import AutoTokenizer, AutoModelForCausalLM

model_name = "Qwen/Qwen3-0.6B"

# 1. 加载 tokenizer
tokenizer = AutoTokenizer.from_pretrained(model_name)

# 2. 加载模型
model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype="auto",
    device_map="auto"
)

print("模型加载完成")
print("模型设备：", model.device)


def generate(
        prompt,
        temperature=0.7,
        top_p=0.8,
        top_k=20,
        enable_thinking=False
):
    messages = [
        {
            "role": "user",
            "content": prompt
        }
    ]

    # 转换为 Qwen3 对话格式
    text = tokenizer.apply_chat_template(
        messages,
        tokenize=False,
        add_generation_prompt=True,
        enable_thinking=enable_thinking
    )

    inputs = tokenizer(
        text,
        return_tensors="pt"
    ).to(model.device)

    with torch.no_grad():
        outputs = model.generate(
            **inputs,
            max_new_tokens=256,
            do_sample=True,
            temperature=temperature,
            top_p=top_p,
            top_k=top_k
        )

    # 去掉输入 prompt 对应的 token
    generated = outputs[0][inputs["input_ids"].shape[-1]:]

    return tokenizer.decode(
        generated,
        skip_special_tokens=True
    )


prompt = """
请用100字左右解释什么是人工智能Agent。
"""


for temperature in [0.2, 0.7, 1.2]:
    print("=" * 70)
    print("Temperature =", temperature)

    result = generate(
        prompt,
        temperature=temperature,
        top_p=0.8,
        top_k=20,
        enable_thinking=False
    )

    print(result)
```

Qwen 官方目前给非思考模式的推荐值大致是 `temperature,top_p=0.8,top_k=20`; 思考模式则推荐 `0.6/0.95/20` , 并特别提示思考模式不要使用 greed decoding。

### Temperature 到底改变了什么？

模型产生 logits :

```
agent    5.2
model    4.8
system   3.1
banana   0.4
```

Softmax : $P_i= \frac{e^{z_i/T}} {\sum_j e^{z_j/T}}$

**Temperature 小**

比如： T = 0.2, 差距被放大：

```
agent  ██████████████████
model  ███
system ▏
```

模型倾向于总选最高概率词。表现：

- 稳定
- 保守
- 重复运行相似度高
- 适合分类，抽取等确定性任务

**Temperature 高**

例如 ： T = 1.2 分布被摊平：

```
agent  ███████
model  ██████
system ████
other  ██
```

更多词有机会被采样，表现：

- 内容变化丰富
- 更有变化
- 创造性增强
- 但事实错误风险也会上升

所以不是 Temperature 越低模型越聪明，而是 **Temperature 控制生成时愿意冒多大的 ‘概率风险’**

### Zero-shot,Few-shot,CoT 怎么做实验？

可以设计一个稍微模糊的客服情感分类任务：

```
手机外观挺漂亮，物流也很快，
但是用了半小时就开始严重发热，
最后只能申请退货。
```

分类：

```
正面
中性
负面
混合
```

**Zero-shot**

```
请判断下面评论的整体情感。

可选类别：
正面、负面、中性、混合。

评论：
手机外观挺漂亮，物流也很快，
但是用了半小时就开始严重发热，
最后只能申请退货。

只输出类别。
```

模型没有任何案例。考察：

```
模型本身对任务的理解能力
```

**Few-shot**

```
请判断评论的整体情感。

示例1：
评论：音质很好，续航也很满意。
情感：正面

示例2：
评论：屏幕很好，但电池续航太差，最后退货。
情感：混合

示例3：
评论：包装一般，没有明显优点或缺点。
情感：中性

现在判断：

评论：
手机外观挺漂亮，物流也很快，
但是用了半小时就开始严重发热，
最后只能申请退货。

情感：
```

现在模型通过示例知道：

```
'有好有坏应该叫混合'，而不是简单判断成负面
```

**CoT / 多步推理**

可以写：

```
分析下面评论。

先完成：
1. 找出评论中的正面信息；
2. 找出评论中的负面信息；
3. 判断哪一部分对最终购买体验影响最大；
4. 最终从“正面、负面、中性、混合”中选择类别。

最后严格输出：
{"sentiment": "..."}
```

这里把复杂问题拆陈了几个中间判断

**三种方法的典型差异**

| 方法         | 优点                     | 缺点                                   |
| ------------ | ------------------------ | -------------------------------------- |
| Zero-shot    | Prompt 短、成本最低      | 容易理解错任务边界                     |
| Few-shot     | 格式稳定、类别边界更明确 | 输入 Token 增多                        |
| CoT/多步推理 | 复杂、模糊任务通常更好   | 更慢、Token 更多，小模型推理也可能跑偏 |

**这张表是理论预期，不应该假装成本地实测结果。**

真正提交实验报告时最好运行：

```
10～50 个测试样本
×
3 种 Prompt
```

统计 Accuracy ，以及 格式正确率，平均生成时间，平均输出 Token

### 开源模型和闭源模型怎么比较

| 维度       | 闭源 API 模型            | 开放权重/可本地部署模型  |

| 定制能力   | 受 API 能力限制          | 很高                     |

| 升级       | 服务商负责               | 自己决定                 |
| 供应商依赖 | 高                       | 较低                     |

### 企业级客服 Agent 我会怎么选？

我一定不会简单回答： ‘一定开源’ 或者 ‘一定闭源’ 更合理的是 **混合架构**：

```
                 用户
                  ↓
             Intent Router
                  ↓
       ┌──────────┴──────────┐
       ↓                     ↓
常规客服/敏感业务          超复杂推理
私有部署模型               强 API 模型
       ↓                     ↓
企业知识库 RAG          脱敏后调用

                  ↓

```

如果必须只选一种，对于 银行，医疗，保险，财务，大型企业内部客服，我更倾向：$\boxed{私有化部署模型 + RAG}$ 

原因不是‘开源更厉害’，而是：

- 用户数据敏感
- 企业内部知识不能外泄
- 答案必须依据企业政策
- 需要可审计
- 可以领域微调
- 成本在稳定高并发下可控

企业客服真正重要的通常不是：‘模型背了多少知识’，而是**能不能准确找到企业自己的最新知识，并且不乱说**

## 习题5

模型幻觉（Hallucination）[11]是大语言模型当前存在的关键局限性之一。本章介绍了缓解幻觉的方法（如检索增强生成、多步推理、外部工具调用）

- 请选择其中一种，说明其工作原理和适用场景
- 调研前沿的研究和论文，是否还有其他的缓解模型幻觉的方法，他们又有哪些改进和优势？

### 为什么模型会幻觉？

Decoder-Only LLM 本质训练目标还是：**预测下一个最可能的Token**，它的优化目标并不是**保证每句话是真实事实**。

例如问：某篇不存在的论文是谁写的，模型可能发现：

```
论文标题
+
作者姓名
+
年份
```

这种语言模式很像训练数据，于是生成一个语言上非常自然的：

```
“该论文由 Smith 等人在 2022 年提出……”
```

但是 Smith 根本不存在，模式不是在数据库：

```
SELECT author FROM papers...
```

而是在**上下文预测下一串 token ** 这就是幻觉最核心的根源之一。

### RAG 的工作原理

普通 LLM :

```
问题
 ↓
LLM 参数记忆
 ↓
答案
```

RAG : 

```
            问题
             ↓
        Query Encoding
             ↓
          检索知识库
             ↓
       找到相关文档片段
             ↓
       问题 + Evidence
             ↓
            LLM
             ↓
         基于证据回答
```

从：$P(answer|question)$  变成近似 $P(answer|question,evidence)$

RAG 最初的核心思想，就是把模型参数里的‘参数化记忆’与外部的‘非参数化记忆’结合。原始 RAG 工作发现，在知识密集任务上能够产生更具体，更事实性的文本。

**一个企业客服例子**

用户： 退款需要几天？

模型自己回答：`一般 3 ~ 5 天` ，危险， 因为公司可能是需要  `七个工作日`

RAG :

```
Query:
退款需要几天
      ↓
检索
      ↓
《售后政策2026版》第4.2节：
退款审核完成后7个工作日内原路退回
      ↓
LLM
      ↓
根据《售后政策2026版》第4.2节，
退款将在审核完成后7个工作日内原路退回。
```

最大的变化：答案从‘模型记忆’ 转向‘证据驱动’。

### RAG 最适合什么

特别适合：

- 企业知识库
- 客服
- 论文阅读
- 法律文档
- 产品手册
- 最新新闻
- 内部制度
- 经常更新的知识
- 需要给出处的回答

**但普通 RAG 也不是万能药**

如果检索错了：

```
Question
   ↓
Retriever
   ↓
错误文档
   ↓
LLM
   ↓
一本正经地根据错误证据回答
```

这叫：**garbage in, garbage out** , 所以最近几年很多研究都在解决 ‘RAG 自己会不会把垃圾端上餐桌’

###  **Self-RAG** : **让模型自己决定要不要检索**

普通 RAG :

```
所有问题
 ↓
都检索
 ↓
都塞文档
```

Self-RAG :

```
问题
 ↓
需要外部知识吗？
 ├── 不需要 → 直接回答
 └── 需要
       ↓
      检索
       ↓
  文档相关吗？
       ↓
  回答得到支持吗？
       ↓
      输出
```

Self-RAG 引入 reflection tokens ,让模型学会：

- 是否需要 retrieval
- 文档是否 relevant
- 回答是否被证据支持
- 最终答案是否有用

它把 ： Retrieve -> Generate 升级成：Retrieve -> Generate -> Critique

论文报告 Self-RAG 在开放域问答，推理，事实验证和长文本生成的事实性，引用准确性上优于多种普通 RAG 基线。减少无意义检索，错误文档污染，不必要的上下文长度。

### CRAG : 检索错了怎么办？

CRAG : Corrective Retireval-Augmented Generation ，增加了一个  **Retrieval Evaluator** :

```
	    Question
  		   ↓
	    Retrieve
 	       ↓
	    Evaluator
 	       ↓
┌────────┬─────────┬─────────┐
正确      模糊       错误
↓          ↓          ↓
使用     进一步处理   Web搜索
```

还会：

```
文档
 ↓
decompose
 ↓
筛掉无关内容
 ↓
recompose
```

CRAG 的核心改进就是**先评价检索质量，再决定下一步检索行为**，必要时使用更大范围搜索补救，这非常适合 agent，因为现实中 Retriever 从来不是 100% 准。

### FLARE : 不是只在开头检索一次

传统：

```
Retrieve
 ↓
Generate 1000字
```

但生成到 800 字可能突然需要一个新事实。

FLARE:

```
生成
 ↓
模型不确定
 ↓
暂停
 ↓
针对即将生成的内容再次检索
 ↓
继续生成
 ↓
又不确定
 ↓
再检索
```

即：**Active Retrieval** ，它会根据低置信内容在生成过程中动态触发检索，更适合长文本和知识密集型生成

### RAPTOR : 解决‘整篇论文’的问题

普通 RAG 把论文切：
```python
Chunk1
Chunk2
Chunk3
...
Chunk100
```

问题 ： 这篇论文整体贡献是什么？这可能不是某一个 Chunk 能回答的，RAPTOR 构建：

```
                   整篇摘要
                 /        \
          大章节摘要      大章节摘要
          /    \            /   \
       Chunk Chunk        Chunk Chunk
```

也就是 ： **树状，多层次语言索引**，查询局部细节：

```
→ 找叶子节点
```

询问整体贡献：

```
→ 找高层摘要
```

RAPTOP 通过递归聚类与摘要建立多层结构，在需要多步推理和长文档整体理解的任务上表现出优势

### Chain-of-Verification : 让模型先写，再审

CoVe的流程是：

```
第一次回答
     ↓
生成核验问题
     ↓
独立回答这些核验问题
     ↓
检查第一次回答
     ↓
修订
     ↓
最终答案
```

例如：

```
初稿：
Transformer由Google于2018年提出。
```

生成核验问题：

```
Transformer论文是哪一年发表？
```

独立核验： `2017` 

于是修改 ： Transformer 于 2017年提出，CoVe 论文报告它可以在多类事实型任务中降低幻觉。

### SelfCheakGPT : 让模型多回答几次，看自己是否打架：

它有一个很有趣的假设：如果模型真的知道答案：

```
回答1：2017
回答2：2017
回答3：2017
回答4：2017
```

比较一致，如果在编：

```
回答1：2016
回答2：2018
回答3：2017
回答4：2019
```

就开始‘人格分裂式投票’了，SelfCheck 不要求访问模型内部 logits ,也不必须依赖外部知识库，通过多次随机采样的一致性检测潜在事实错误，适合 ：黑盒 API 模型

### Semantic Entropy : 不看文字差异，看‘答案意思’是否稳定

这是更进一步的方法，假如五次回答：

```
Beijing
Beijing City
the city of Beijing
北京市
Beijing
```

表面 token 不一样，但语义完全一样，所以不能说：‘答案不稳定’，Semantic Entropy 对生成结果按照**语义等价关系**聚类，再估计语义层面的不确定性。如果：

```
北京
上海
广州
深圳
南京
```

出现大量语义不同答案： $Entropy\uparrow$  说明模型可能根本不知道，2024 年发表在 Nature 的研究表面，这种语义不确定性能够检测一类由知识缺失导致的 confabulation , 实际系统可以：

```
低 entropy
→ 正常回答

高 entropy
→ 再检索
→ 调用工具
→ 人工审核
→ 或拒答
```

这个思想对 Agent 非常重要： **真正可靠的 AI 不只是会回答，还应该知道什么时候不应该相信自己**

### DoLa ： 甚至不用 RAG , 修改解码过程

DoLa : Decoding by Contrasting Layers 研究发现不同 Transformer 层内部表达的知识程度不同，于是比较：

```
较浅层 logits
vs
较深层 logits
```

强调深层网络中更成熟的事实信息，优点：

- 不需要外部训练库
- 不需要重新训练
- 只改 decoding

原论文在多个事实性任务中观察到真实性改善，但他解决不了：模型根本没学过 2026 年刚发生的事情，所以它无法替代 RAG 。

**可以把幻觉治理理解成一道 ‘多层防火墙’** 

```
第一层
高质量训练数据
        ↓
第二层
可靠模型
        ↓
第三层
RAG / 外部知识
        ↓
第四层
Retrieval Evaluator
        ↓
第五层
CoVe / 自我验证
        ↓
第六层
工具调用
        ↓
第七层
不确定性检测
        ↓
第八层
引用 / Evidence
        ↓
第九层
拒答 / 人工介入
```

不是找到一种算法：幻觉从此消失，而是 ：多层机制共同降低错误进入最终答案的概率。

## 习题6

假设你要设计一个论文辅助阅读智能体，它能够帮助研究人员快速阅读并理解学术论文，包括：总结论文研究的核心内容、回答关于论文的问题、提取关键信息、比较多篇不同论文的观点等。请回答：

- 你会选择哪个模型作为智能体设计时的基座模型？选择时需要考虑哪些因素？
- 如何设计提示词来引导模型更好地理解学术论文？学术论文通常很长，可能超过模型的上下文窗口限制，你会如何解决这个问题？
- 学术研究是严谨的，这意味着我们需要确保智能体生成的信息是准确客观忠于原文的。你认为系统中加入哪些设计能够更好的实现这一需求？

### 选择什么基座的模型？

如果是真的做： **研究人员使用的论文辅助 Agent** ，我更倾向 ：Qwen3-32B + RAG 作为一个开放权重方案。Qwen3-32B 官方模型卡给出的规模约 32.8 B,原生 32768 上下文，并可以通过 YaRN 拓展到 131072 tokens，同时支持中英文和多语言以及推理/非推理模式

为什么不是一味追求‘超长上下文’ ？

因为论文阅读能力不仅由 `Context Length` 决定，还需要考虑：推理能力，学术语言理解，中英文能力，数学代码理解，长上下文利用率，JSON等结构化输出，TOOL Calling, 幻觉率 ....

**128K 上下文是不是就可以把所有论文直接塞进去 ？** 

不建议，这是一个非常重要的误区：$\boxed{ Context\ Window\ 大 \neq 模型能完美利用整个 Context } $ ,`Lost in the Middle` 研究发现，即使是长上下文模型，当关键信息位于超长上下文中间时，表现也可能明显下降。也就是说：能装进128K 和 能准确找到 128K 中的任何一句话这完全是两回事，这有点像：给你一本 1000 页的书放在桌上，不代表任何一个细节你都能瞬间从 537 页准确找出来。

**所以论文应该怎么处理 ？**

不要：

```
整篇PDF
 ↓
直接塞LLM
```

而是 **文档结构化 + RAG** , 例如论文：

```
Title
Abstract
1 Introduction
2 Related Work
3 Method
  3.1 Architecture
  3.2 Loss
4 Experiments
  4.1 Dataset
  4.2 Setup
  4.3 Results
5 Discussion
6 Conclusion
References
```

切块时保留 Metadata ：

```python
{
  "paper": "EEG-Conformer",
  "section": "4.2 Experimental Setup",
  "page": 6,
  "chunk_id": 37,
  "text": "..."
}
```

以后问：EEG-Conformer 用了多少个 Transformer block ，系统不是搜索一团文本，而是得到：

```python
Paper: EEG-Conformer
Section: Method
Page: 4
Chunk: 21
```

**Chunk 怎么切也很重要**

最差方案：`每 500 个字符切一刀` ，但是可能把 `实验结果：The accuracy of EEG-Conformer` 切在 Chunk 1，然后 `is 80.83%.` 切到 Chunk 2

更好的 ： **Section-aware Chunking** 按照：标题，段落，章节，公式，表格，图，引用关系 切，并加一定 overlap:

```
Chunk1
████████████████

Chunk2
             ████████████████
             ↑ overlap
```

防止语义被切断

**长论文用层级摘要**

比如：

```
Section 1
 ↓
summary1

Section 2
 ↓
summary2

Section 3
 ↓
summary3
```

然后：

```
summary1
summary2
summary3
   ↓
全局摘要
```

形成：

```
                    Paper Summary
                   /      |       \
          Intro Summary Method Summary Experiment Summary
             /               |              \
         Chunk...          Chunk...          Chunk...
```

这和 RAPTOR 的树状思想非常接近。

### 怎样设计 Prompt ？

我首选会给模型一个非常严格的 System Prompt ，例如：

你是一名学术论文阅读助手。你的任务是基于提供的论文原文进行分析，而不是依靠你自己的背景知识猜测。

回答时遵守以下猜测：

1. 只把论文中明确出现的信息表述为论文事实
2. 每个关键事实必须给出论文页码，章节或证据编号
3. 区分‘作者原文结论’和‘你的分析/推断’
4. 如果提供的证据不足，回答‘当前证据中未找到’，不得补全或猜测
5. 对实验结果必须注明数据集，指标和对于实验设置
6. 比较不同论文时，先分别提取每篇论文的证据，再进行比较
7. 不得编造论文，作者，引用，数字，数据集或实验结果

然后不同任务再加具体模板

**总结论文时不要只问‘总结这篇论文’**

太开放，应该拆成 Schema ： 

```
请提取：

1. Research Problem
2. Motivation
3. Core Idea
4. Model Architecture
5. Dataset
6. Experimental Setup
7. Baselines
8. Evaluation Metrics
9. Main Results
10. Ablation Study
11. Limitations
12. Future Work
```

### ''作者说的''和"AI推断的"必须分开

例如：**原文事实** ：作者使用 Adam 优化器

​	   **Agent分析** ： Adam 可能是因为模型参数较多，需要较稳定的自适应学习率

第二句话**不是论文事实**，所以系统应该明确：

```  
【论文明确陈述】
作者使用 Adam。

【模型分析】
论文没有明确解释原因。可能考虑了……
```

如果不区分，AI很容易把“我的合理推测” 偷偷升级成“作者的设计理由”，学术阅读中这是非常危险的一种幻觉。

**多论文比较应该怎么做？**

不要直接：

```
Paper A + Paper B + Paper C
 ↓
LLM
 ↓
比较
```

容易串信息,更稳妥的是：

```
Paper A
 ↓
结构化事实 A

Paper B
 ↓
结构化事实 B

Paper C
 ↓
结构化事实 C

       ↓
标准化 Schema
       ↓
Comparison Agent
```

例如统一抽成：

| 项目     | Paper A           | Paper B           |
| -------- | ----------------- | ----------------- |
| Task     | MI Classification | MI Classification |
| Dataset  | BCI IV 2a         | BCI IV 2a         |
| Input    | EEG               | EEG               |
| Backbone | CNN               | CNN+Transformer   |
| Accuracy | ...               | ...               |
| Params   | ...               | ...               |

先把‘事实抽取’完成，再‘观点比较’，可以大幅度减少不同论文之间的信息污染。

### 如果进一步保证严谨性？

我会设计四个 Agent/阶段 ， 而不是让一个模型包打天下：

```
                    用户问题
                       ↓
                  Retrieval Agent
                       ↓
                  Evidence Pack
                       ↓
                   Answer Agent
                       ↓
                  Draft Answer
                       ↓
                 Verification Agent
                       ↓
               每个 claim 是否有证据？
                  ↙             ↘
                有               无
                ↓               ↓
              保留          删除/重新检索
                  \             /
                       ↓
                  Citation Agent
                       ↓
                  Final Answer
```

**Verification Agent 检查什么？**

一句：`“该模型在BCI IV 2a上达到89.4%准确率。”` 拆成：

```
Claim 1：
模型 = X

Claim 2：
Dataset = BCI IV 2a

Claim 3：
Metric = Accuracy

Claim 4：
Value = 89.4%
```

分别问 `Evidence 中真的出现了吗？` , 只要 89.4 % 找不到 `unsupported` 就不能输出，这已经不只是‘Prompt Engineering’了，而是 **Evidence Engineering** 

### 再加入‘不知道’机制

这其实比换一个更大的模型更重要，模型应该允许输出：

```
当前提供的论文证据中未找到作者对此设计的明确解释。
```

而不是：

```
让我来推理一下作者为什么这么干……
```

所以建立：$Confidence < threshold$  时：

```
重新检索
    ↓
仍然没有
    ↓
Abstain
```

即：**允许拒答** ，可靠系统的能力不仅是：`知道 -> 回答`，还包括`不知道 -> 承认不知道`
