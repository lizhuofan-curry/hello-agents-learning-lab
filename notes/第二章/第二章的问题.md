## 习题1

物理符号系统假说[1]是符号主义时代的理论基石。请分析：

- 该假说的"充分性论断"和"必要性论断"分别是什么含义？
- 结合本章内容，说明符号主义智能体在实践中遇到的哪些问题对该假说的"充分性"提出了挑战？
- 大语言模型驱动的智能体是否符合物理符号系统假说？

### 1.物理符号系统假说

**充分性，必要性分别是什么意思？**

物理符号系统由以下部分构成：

- 一组可以区分的符号；
- 由符号组合成的复杂结构；
- 创建，修改，复制，删除符号结构的操作；
- 根据规则符号进行搜索和推理的过程

例如专家系统中的：发烧，咳嗽，呼吸道感染都是符号，而 IF 发烧 AND 咳嗽 THEN 可能患有呼吸道感染；就是对符号进行操作的规则

**充分性论断**

> 物理符号系统具备产生通用智能行为的充分手段

可以写成 P => I ,其中 P系统具有完整的物理符号处理能力，I系统能够产生通用智能行为。它的核心含义是：只要拥有合适的符号表示，知识和操作规则，原则上就足以构造智能，不必再引入某种神秘的物质‘但不能把它误解为：随便写几个符号和规则，机器就一定会智能。

'具备充分手段'强调的是理论可能性，不保证知识工程简单，也不保证任意符号程序都有智能

**必要性论断**

必要性是指 I => P ,也就是说如果必要性成立，那么无论是人脑，计算机还是机器人，只要拥有智能，其内部最终都必须能够被解释为符号表示和符号操作

**二者的区别**

| 论断   | 研究方向           | 核心问题                       |
| ------ | ------------------ | ------------------------------ |
| 充分性 | 从符号系统推向智能 | 仅靠符号操作能否造出智能？     |
| 必要性 | 从智能反推符号系统 | 所有智能都必须依赖符号操作吗？ |

### 哪些实践问题挑战了‘充分性’？

1. **知识获取瓶颈**

   符号系统需要人类提前把知识写进去，例如医疗专家知道：

   ```
   患者高烧、血培养阳性且免疫功能低下时，需要综合评估感染风险。
   ```

   但是医生的判断还可能依赖：

   - 多年临床经验
   - 对患者病例的敏感性
   - 对异常病例的敏感性
   - 对多个弱信号的综合判断

   这些隐性知识很难全部写成明确的`IF-THEN` 规则。

   因此问题不是推理机完全不会推理，而是：系统无法低成本地获得足够完整的知识

2. **常识问题**

   人类默认知道：

   - 杯子掉在地上可能会碎
   - 绳子可以拉，通常不能推
   - 人不可能同时出现在距离很远的两个地方
   - ‘我不开心’中的‘不’改变了整句话的含义

   符号系统若没有显式写入这些知识，便不会自动知道，而现实世界中的常识数量巨大，边界模糊，还存在大量例外，难以穷举

3. **框架问题**

   假设机器人把一个积木拿起来，需要更新哪些事实？

   发生的变化有：

   ```
   积木的位置
   机械手的状态
   桌面上积木的数量
   ```

   没有发生变化的可能有：

   ```
   房间颜色
   其他积木形状
   今天的日期
   墙壁的位置
   ......
   ```

   如果系统每执行一个动作，都要显式说明无数个‘没有变化的事实’，计算将非常低效

4. **系统脆弱性**

   规则系统只能处理设计者预计到的情况

   例如：

   ```
   IF 体温 > 38度
   THEN 发烧
   ```

   但真实输入可能是：

   ```
   体温记录缺失
   温度计故障
   患者刚进行剧烈运动
   患者服用了退烧药
   ```

   如果规则库没有覆盖这些情况，系统可能：无法得出结论，给出错误结论，触发相互冲突的规则

**是否因此‘证伪了’充分性？**

不一定，这些问题强烈挑战了“仅靠人工符号就能实际构造通用智能”的乐观判断，但未必在逻辑上证明物理符号系统假说为假。

更严谨的结论是：

```
实践表明，符号系统即使理论上具有表达和推理能力，如何获得完备知识，管理现实世界的不确定性并实现可拓展推理，仍是巨大困难
```

换句话说，它挑战的是假说的强工程性解释，而不一定完成了严格的理论证伪

### LLM 智能体是否符合物理符号系统假说？

这个问题不能简单的回答符合以及不符合

**符合的一面**

LLM 智能体会处理大量离散符号：

- 文本被转换成Token；
- 提示词是符号序列
- 工具名称和参数通常使用JSON
- 程序代码是符号
- 规划步骤，记忆记录也是符号结构
- 工具调用会创建，修改和传递符号

因此，从整个智能体系统来看，它确实包含大量符号处理过程

**不符合传统符号主义的一面**

LLM 内部的知识并不是以清晰的规则存储：

```
IF 条件
THEN 结论
```

而是分布在神经网络的大量参数中。

例如，“巴黎是法国首都”通常没有对应某一条独立规则，而是隐式编码在许多权重之间。因此：

- 知识是分布式的
- 推理过程未必能还原成明确规则

- 模型输出具有概率性，同一问题可能产生不同回答

这更符合联结注意，而不是古典符号主义

**综合结论**

现代 LLM 智能体更适合被称为：神经-符号混合系统，其中：

- 神经网络复杂语言理解，知识压缩，模糊推理和生成
- 符号模块负责代码执行，工具调用，数据库查询，规则约束和精确计算
- 记忆，规划和环境反馈把二者连接成智能体循环

因此，LLM智能体没有简单证明或者推翻符号系统假说，而是说明：智能可能由分布式神经表示与显示符号操作共同产生

## 习题2

专家系统MYCIN[2]在医疗诊断领域取得了显著成功，但最终并未大规模应用于临床实践。请思考：

> **提示**：可以从技术、伦理、法律、用户接受度等多个角度分析

- 除了本章提到的"知识获取瓶颈"和"脆弱性"，还有哪些因素可能阻碍了专家系统在医疗等高风险领域的应用？
- 如果让现在的你设计一个医疗诊断智能体，你会如何设计系统来克服MYCIN的局限？
- 在哪些垂直领域中，基于规则的专家系统至今仍然是比深度学习更好的选择？请举例说明。

### 除了知识瓶颈和脆弱性外，还要哪些障碍

MYCIN拥有大约600条医疗规则，并使用置信因子处理不确定性。它在实现条件下表现优秀，但诊断正确并不等于能安全进入真实临床。

**技术问题**

1. **输入质量不稳定**

   临床数据可能缺失，错误或互相矛盾。例如患者描述，检验结果和病例记录不完全一致。

2. **适用范围有限**

   MYCIN主要针对细菌性血液感染。如果患者同时存在肝肾功能异常，过敏等多种并发症，原有规则可能无法覆盖

3. **不确定性模型有限**

   置信因子可以表示可信程度，但不等同于经过统计校准的真实患病概率

4. **难以持续更新**

   医学指南，耐药菌分布和药品方案不断变化，知识库必须长期维护

5. **缺少医院系统集成**

   如果不能直接连接电子病历，检验系统，医学影响，药品系统，医生就要重复输入数据，负担上升

**伦理问题**

- 不同人群是否得到同样准确的诊断？

- 系统是否会放大历史数据中的偏差？

- 患者是否知道AI参与了诊断？

- 系统能否解释为什么推荐某种抗生素？

- 医生会不会产生“自动化依赖”，不再认真复核

**法律责任**

如果系统给出错误建议，需要明确：

- 软件开发者是否负责；

- 医院是否负责；

- 最终采用建议的医生是否负责；

- 数据录入错误由谁负责；

- 系统更新后是否需要重新验证。

**用户接受度**

医生可能不愿意相信一个：

- 不理解完整临床背景；

- 无法清楚解释依据；

- 可能打断现有工作流程；

- 还要求医生承担最终责任的系统。

患者也可能不接受“由计算机决定治疗方案”

### 如何设计现代医疗诊断智能体？

我会把它定位为“临床决策支持系统”，而不是完全代替医生的自动诊断系统

**推荐架构**

```
患者信息、检验、影像、病历
          ↓
数据校验与标准化
          ↓
规则系统 + 统计模型 + 医学大模型
          ↓
检索最新指南和可信医学知识
          ↓
生成候选诊断、依据和不确定性
          ↓
安全规则与药物禁忌检查
          ↓
医生复核、修改或拒绝
          ↓
记录结果并持续监测
```

**核心模块：**

1. 感知模块

   读取电子病历、检验结果、生命体征和影像报告，并检测缺失值、单位错误和互相矛盾的信息。

2. 医学知识模块

   使用经过审核的医学指南、药品说明和医院内部规范，不让模型只凭参数中的模糊记忆回答。

3. 混合推理模块

   明确禁忌使用规则系统；风险预测使用经过验证的统计或机器学习模型；病历总结和候选诊断解释使用LLM；剂量等精确计算交给确定性程序。

4. 不确定性与越界检测

   系统必须能够说：当前信息不足，无法可靠判断



### 哪些领域更适合规则专家系统？

当问题具有以下特点时，规则系统往往优于单独使用深度学习：

- 规则明确且相对稳定；
- 必须给出确定、可解释的结果；
- 错误成本高；
- 训练数据少；
- 每一条判断都需要审计；
- 不允许模型自由发挥。

经典例子包括：

| 领域             | 适合规则系统的原因             |
| ---------------- | ------------------------------ |
| 税务和费用计算   | 法规可明确编码，结果必须精确   |
| 银行交易合规初筛 | 审查条件明确，需要审计记录     |
| 工业安全联锁     | 满足危险条件必须立即停止设备   |
| 网络访问控制     | 权限关系明确，不能概率性放行   |
| 药物禁忌检查     | 已知过敏、剂量上限等属于硬约束 |
| 产品配置检查     | 部件之间的兼容关系明确         |
| 保险资格初筛     | 条款和条件通常可以显式表示     |

最佳实践通常不是规则或者深度学习二选一，而是：

```
深度学习负责识别复杂模式
规则系统负责守住确定性边界
人类负责高风险最终决策
```

### 增加规则和上下文记忆

在教材代码基础上的一个可运行版本。它增加了工作，学习，爱好，情绪规则，并能记住姓名，年龄和职业

```python
import re
import random


rules = [
    # 工作
    (
        r'I work (?:as|in) (.*)',
        [
            "How do you feel about working as/in {0}?",
            "What do you like most about your work in {0}?",
            "Does working in {0} make you feel fulfilled?"
        ]
    ),

    # 学习
    (
        r'I am studying (.*)',
        [
            "What interests you about {0}?",
            "What is the most difficult part of studying {0}?",
            "How long have you been studying {0}?"
        ]
    ),

    # 爱好
    (
        r'I like (.*)',
        [
            "Why do you like {0}?",
            "How often do you spend time on {0}?",
            "What makes {0} enjoyable for you?"
        ]
    ),

    # 情绪
    (
        r'I feel (.*)',
        [
            "Why do you feel {0}?",
            "What usually makes you feel {0}?",
            "How long have you felt {0}?"
        ]
    ),

    # 需求
    (
        r'I need (.*)',
        [
            "Why do you need {0}?",
            "Would getting {0} really help you?",
            "What would happen if you did not get {0}?"
        ]
    ),

    # 家庭
    (
        r'.*\bmother\b.*',
        [
            "Tell me more about your mother.",
            "How do you feel about your mother?"
        ]
    ),

    (
        r'.*\bfather\b.*',
        [
            "Tell me more about your father.",
            "How do you feel about your father?"
        ]
    ),

    # 兜底规则必须放在最后
    (
        r'.*',
        [
            "Please tell me more.",
            "Can you elaborate on that?",
            "What does that mean to you?"
        ]
    )
]


pronoun_swap = {
    "i": "you",
    "you": "I",
    "me": "you",
    "my": "your",
    "your": "my",
    "am": "are",
    "are": "am",
    "mine": "yours",
    "yours": "mine"
}


def swap_pronouns(phrase):
    """转换第一、第二人称代词。"""

    def replace_word(match):
        word = match.group(0).lower()
        return pronoun_swap.get(word, word)

    return re.sub(
        r"\b(i|you|me|my|your|am|are|mine|yours)\b",
        replace_word,
        phrase,
        flags=re.IGNORECASE
    )


def remember_information(user_input, memory):
    """从用户输入中提取姓名、年龄和职业。"""

    name_match = re.search(
        r'my name is ([A-Za-z]+)',
        user_input,
        re.IGNORECASE
    )

    if name_match:
        memory["name"] = name_match.group(1)
        return f"Nice to meet you, {memory['name']}."

    age_match = re.search(
        r'I am (\d{1,3}) years old',
        user_input,
        re.IGNORECASE
    )

    if age_match:
        memory["age"] = age_match.group(1)
        return f"I will remember that you are {memory['age']} years old."

    job_match = re.search(
        r'I work as (?:an? )?([A-Za-z ]+?)[.!?]?$',
        user_input,
        re.IGNORECASE
    )

    if job_match:
        memory["job"] = job_match.group(1).strip()
        return f"I will remember that you work as {memory['job']}."

    return None


def answer_memory_question(user_input, memory):
    """回答与已保存信息有关的问题。"""

    if re.search(r'what(?:\'s| is) my name', user_input, re.IGNORECASE):
        if "name" in memory:
            return f"Your name is {memory['name']}."
        return "You have not told me your name yet."

    if re.search(r'how old am I', user_input, re.IGNORECASE):
        if "age" in memory:
            return f"You are {memory['age']} years old."
        return "You have not told me your age yet."

    if re.search(
        r'what(?:\'s| is) my (?:job|occupation)',
        user_input,
        re.IGNORECASE
    ):
        if "job" in memory:
            return f"You work as {memory['job']}."
        return "You have not told me your occupation yet."

    return None


def respond(user_input, memory):
    # 先判断用户是否在询问历史信息
    memory_answer = answer_memory_question(user_input, memory)

    if memory_answer:
        return memory_answer

    # 再尝试保存用户新提供的信息
    remember_answer = remember_information(user_input, memory)

    if remember_answer:
        return remember_answer

    # 最后进行普通的规则匹配
    for pattern, responses in rules:
        match = re.search(pattern, user_input, re.IGNORECASE)

        if match:
            captured_group = match.group(1) if match.groups() else ""
            swapped_group = swap_pronouns(captured_group)
            response = random.choice(responses).format(swapped_group)

            # 在普通回答中引用姓名
            if "name" in memory and random.random() < 0.3:
                response = f"{memory['name']}, {response}"

            return response

    return "Please tell me more."


if __name__ == "__main__":
    memory = {}

    print("Therapist: Hello! How can I help you today?")

    while True:
        user_input = input("You: ")

        if user_input.lower() in ["quit", "exit", "bye"]:
            print("Therapist: Goodbye.")
            break

        print("Therapist:", respond(user_input, memory))
```

对话示例：

```
You: My name is Tom.
Therapist: Nice to meet you, Tom.

You: I am 20 years old.
Therapist: I will remember that you are 20 years old.

You: I work as a programmer.
Therapist: I will remember that you work as programmer.

You: What is my name?
Therapist: Your name is Tom.

You: I like playing basketball.
Therapist: Tom, Why do you like playing basketball?
```

这里的记忆其实只是一个字典：

```python
memory = {
    "name": "Tom",
    "age": "20",
    "job": "programmer"
}
```

它并不真正理解用户，只是把匹配到的字符串保存下来

### 拓展 ELIZA 与 ChatGPT 的本质差异

| 维度     | ELIZA                  | ChatGPT类大模型              |
| -------- | ---------------------- | ---------------------------- |
| 知识来源 | 程序员手写规则         | 从大规模数据中训练获得       |
| 语言处理 | 正则匹配和模板替换     | 基于上下文预测并生成语言     |
| 语义理解 | 基本没有               | 能形成较强的语义表示         |
| 泛化能力 | 只能处理已写规则       | 可以处理大量未明确写过的表达 |
| 上下文   | 需要程序员手工保存字段 | 可结合较长对话上下文推理     |
| 输出形式 | 从有限模板中选择       | 动态逐Token生成              |
| 学习方式 | 增加或修改规则         | 预训练、微调、偏好对齐       |
| 稳定性   | 确定、容易审计         | 灵活但可能产生幻觉           |

但ChatGPT也不是“像人一样真正理解”，它仍可能：

- 编造事实
- 错误推理
- 忽略限制条件
- 对提示方式敏感
- 能给出表达流畅但实际错误的答案

### 为什么会出现组合爆炸？

假设开放对话中存在k个相互独立的因素：

- 主题
- 情绪
- 时态
- 肯定或否定
- 人称
- 句型
- 上下文状态

如果第i个因素有$n_i$种情况，那么理论组合数为：$N=\prod_{i=1}^{k}n_i$

如果有10个因素，每个因素只有5种情况：$N=5^{10}=9,765,625$,这意味着可能要接近一千万种组合，才能较完整地覆盖输入空间。

而自然语言中每种意思还能有大量表达：

```
I am sad.
I feel unhappy.
I am feeling down.
Today has been difficult.
Nothing seems to make me happy.
```

规则数量增加后还会产生冲突。若有 R 条规则，需要检查的两两冲突数量最高可达到：$\frac{R(R-1)}{2}=O(R^2)$

所以规则系统面临两种增长：

- 为覆盖语言变化，规则数量近似指数增长
- 为处理规则冲突，维护成本可能接近平方增长

这就是开放域对话难以靠规则穷举的数学原因

- 模块职责清晰
- 可以并行工作
- 组件容易替换

- 协调成本高
- 不同智能体可能相互冲突
- 很难解释全局行为为什么出现
- 局部最优不一定形成全局最优
- 关键组件失效仍可能阻断整个任务

为了提高容错，可以加入：

- 把复杂任务分解成子任务
- 给不同智能体分配专业职责
- 通过通信和协作完成整体目标
- 整体能力大于任一单独智能体的能力
- 强调组织结构化，任务分配和信息传递

现代框架的区别是：

| 维度       | 心智社会               | 现代LLM多智能体                      |
| ---------- | ---------------------- | ------------------------------------ |
| 单个智能体 | 极简单、“无心”的过程   | 通常是具备知识和推理能力的LLM        |
| 协作机制   | 激活、抑制和局部交互   | 自然语言、消息、结构化任务和工具调用 |
| 控制方式   | 强调去中心化和涌现     | 常有协调者、管理者或明确工作流       |
| 目标来源   | 由局部互动形成复杂行为 | 通常由用户给出明确全局目标           |
| 任务结构   | 心智功能的理论模型     | 面向软件开发、研究、写作等工程任务   |
| 可观测性   | 偏认知理论             | 通常记录任务、消息和工具结果         |

具体来说：

- CAMEL Workforce使用协调智能体分配工作，并由任务规划智能体负责分解和重组任务，属于明显的层级式协作
- MetaGPT将产品经理、架构师、工程师等角色组织成类似软件公司的流水线，强调标准操作流程和结构化产物。
- CrewAI把智能体、任务、Crew和Process组织起来，既支持顺序或层级协作，也支持带状态的受控工作流。

因此，它们继承了“分工协作产生更强整体能力”的思想，但往往比明斯基最初设想的系统更加中心化、结构化和工程化。

### LLM强大是否意味着“心智社会”过时了？

并不意味着

现代LLM虽然单体能力强，但仍无法独立可靠完成所有事情

- 它不能天然访问实时数据库
- 它需要外部工具执行代码
- 它需要记忆系统保存长期记忆
- 它需要检索系统获得可信资料

所以现代智能体本身就是一个“小型心智社会”

```
LLM
├── 规划模块
├── 记忆模块
├── 检索模块
├── 代码执行器
├── 浏览器
├── 安全检查器
└── 结果验证器
```

最大的变化在于：

> 过去是大量能力很弱的模块协作；现在可以由少量能力较强的LLM智能体与确定性工作协作

因此，“心智社会”不是具体的软件框架，而是一种仍然有效的架构思想：复杂智能不必全部压在一个完美模块中

强化学习与监督学习是两种不同的学习范式。请分析：

- 用AlphaGo的例子说明强化学习的"试错学习"机制是如何工作的
- 为什么强化学习特别适合序贯决策问题？它与监督学习在数据需求上有什么本质区别？
- 现在我们需要训练一个会玩超级马里奥游戏的智能体。如果分别使用监督学习和强化学习，各需要什么数据？哪种方法对于这个任务来说更合适？
- 在大语言模型的训练过程中，强化学习起到了什么关键性的作用？

### AIphaGo如何进行试错学习？

教材用AIphaGo说明强化学习的基本循环：

1. 观察当前棋盘状态 $S_t$
2. 根据策略选择落子 $A_t$
3. 对手行动，棋局进入新状态 $S_{t+1}$
4. 对局结束后获得胜负奖励
5. 根据奖励调整策略
6. 重复大量自我博弈

奖励机制可以简化为$R= \begin{cases} +1,& \text{胜利}\\ -1,& \text{失败} \end{cases}$

系统需要学习的就是 $\pi(a\mid s)$

即在状态s下，选择α的策略

需要补充一个历史细节：教材为了突出强化学习而进行了简化。经典AlphaGo 并非不适用人类棋谱，它先从人类棋局中学习策略，再通过自我对弈强化学习继续提升，并结合价值与蒙特卡洛树搜索

### 为什么强化学习适合序贯决策？

序贯决策的特点是：当前行动不仅影响当前结果，也影响未来能够到达的状态。

例如超级马里奥现在跳一下，可能：

- 立即得到金币
- 避开敌人
- 到达高处平台
- 为几秒后的通关创造条件

强化学习优化的是长期积累回报：$G_t=R_{t+1}+\gamma R_{t+2}+\gamma^2R_{t+3}+\cdots$

其中γ是折扣因子，因此它能学习：有些行动眼前没有收益，但会增加未来成功的概率

**与监督学习的数据差异**

监督学习需要： （x,y）,也就是 输入状态 -> 正确答案。例如：

```
当前游戏画面 → 专家此时按下“向右跳”
```

强化学习得到的则是交互数据：$(S_t,A_t,R_{t+1},S_{t+1})$

它不需要每一步都有专家给出正确动作，只需要环境最终提供奖励。

| 方面     | 监督学习           | 强化学习           |
| -------- | ------------------ | ------------------ |
| 数据来源 | 已标注数据         | 与环境交互         |
| 教师信号 | 每个样本的正确答案 | 奖励信号           |
| 数据分布 | 通常固定           | 随策略变化         |
| 主要目标 | 模仿标签           | 最大化长期回报     |
| 探索     | 通常不需要         | 必须探索未知行为   |
| 难点     | 标注成本           | 交互成本、奖励稀疏 |

### 训练超级马里奥智能体需要什么数据？

**使用监督学习**

需要大量专家演示：

```
游戏画面1 → 向右
游戏画面2 → 跳跃
游戏画面3 → 向右+加速
……
```

数据来源可以是人类高手的游戏录像以及对应按键

模型学习的是：在类似画面下模仿人类动作

问题是：

- 需要大量精确对齐的画面-按键数据
- 模型很难超过演示者
- 一旦走到训练数据没出现过的状态，容易连续犯错
- 不会自动理解“通关”才是最终目标

**使用强化学习**

需要：

- 游戏模拟器
- 当前画面或状态
- 可执行按键
- 奖励函数
- 回合结束条件

奖励可以设计为：

```
向右前进：正奖励
获得金币：正奖励
通过关卡：大正奖励
死亡：负奖励
长时间不动：小负奖励
```

强化学习更适合，因为超级马里奥本质上是一个长时间，多步骤的序贯决策问题。

但工程上最好的方式往往是混合方案：

```
人类演示进行监督预训练
          ↓
获得基本操作能力
          ↓
强化学习继续自我探索
          ↓
优化最终通关率
```

### 强化学习在LLM训练中的作用

LLM的主要语言和世界知识来自于预训练，而强化学习主要用于后训练和行为对齐

经典流程是：

```
大规模文本预训练
      ↓
指令微调
      ↓
收集人类偏好
      ↓
训练奖励模型
      ↓
使用强化学习优化回答
```

人类可能比较两个回答：

```
回答A：准确、安全、遵循指令
回答B：答非所问或包含危险内容
```

奖励模型学习人类更偏好哪一个，再用强化学习提高高奖励回答的概率

它的主要作用是：

- 改善回答有用性
- 降低明显有害输出
- 调整语言风格
- 让模型学会在复杂任务中选择更符合目标的行为

但强化学习不是LLM知识的主要来源。更准确的说：

> 预训练解决的是“模型知道什么”，强化学习和其他偏好优化方法更多解决“模型应该怎么回答和行动”

### 为什么预训练缓解了知识获取瓶颈？

符号主义获得知识的流程是：

```
专家拥有知识
    ↓
知识工程师访谈
    ↓
提炼成明确规则
    ↓
人工写入知识库
```

成本随着知识量不断增加

预训练则是：
```
海量文本
   ↓
自监督学习
   ↓
预测被遮盖的词或下一个词
   ↓
自动调整神经网络参数
   ↓
形成隐式语言与世界知识
```

他不需要人类为每句话人工标注知识，例如训练文本中出现大量类似内容：

```
法国的首都是巴黎。
巴黎是法国最大的城市之一。
埃菲尔铁塔位于巴黎。
```

模型通过预测任务逐渐学习这些概念之间的统计关系

**知识表示的本质差异**

| 符号系统             | 预训练模型                   |
| -------------------- | ---------------------------- |
| 知识以规则、事实存储 | 知识分布在权重中             |
| 显式表示             | 隐式表示                     |
| 容易追踪来源         | 很难定位某条知识来自哪里     |
| 更新单条规则较方便   | 更新局部知识可能影响其他能力 |
| 精确但覆盖有限       | 覆盖广但可能模糊或错误       |
| 推理通常确定         | 输出通常具有概率性           |

预训练没有彻底消灭知识获取问题，而是把问题从 “怎样逐条人工输入知识”转化为“怎样获取，清洗，平衡并验证海量训练数据”

### 互联网数据会带来什么问题？

**主要风险**

```
1.错误信息
   网络中有谣言，过时资料和错误教程
2.社会偏见
   数据可能包含性别，种族，地区，职业等偏见
3.有害内容
   包括暴力，仇恨，诈骗和危险操作方法
4.隐私问题
   数据可能包含个人联系方式，身份信息或私人对话
5.版权与授权问题
   训练内容可能来自受版权保护的作品
6.数据投毒
   恶意内容可能视图影响模型行为
7.数据污染
   测评题可能出现在训练数据中，造成测试成绩虚高
```

**缓解方法**

```
数据来源筛选和质量分级
维护数据来源和授权记录
进行安全微调，红队测试和偏差评估
对高风险回答接入可信知识库
使用搜索或RAG获取最新资料
要求模型给出证据并使用工具验证
```

### 预训练-微调会被取代吗？

短期内不会彻底消失，但会从简单的“两阶段结构”演化成更完整的学习循环

未来可能变成：

```
多模态预训练
    ↓
指令与偏好后训练
    ↓
检索和工具增强
    ↓
环境交互学习
    ↓
持续学习与个性化
    ↓
执行结果反馈
```

原因是预训练具有很明显的经济优势：

> 一次训练通用基础能力，可以被许多下游任务复用

但它也可能逐渐减少对静态互联网文本的依赖，增加：

- 视频，音频和传感器数据
- 强化学习
- 持续学习
- 外部知识库
- 世界模型

所以更可能出现的不是“预训练消失”，而是：

> 预训练仍然提供基础能力，但不在独自承担知识，推理，更新和行动的全部任务

### 1980年代符号主义方案

当前可以使用：

- 编译器词法和语法分析
- 抽象语法树
- 手工编写的代码规范
- 类型检查
- 控制流和数据流分析
- 规则专家系统

规则可能是

```python
IF 函数长度 > 100行

IF 函数长度 > 100行

- Token序列

- 控制流图
- API调用序列

```

训练数据可能来自：

- 历史bug修复提交
- 带缺陷标签函数
- 代码与注释对
- 过去的代码审查意见

**相比符号主义的进步**

- 可学习复杂模式
- 不必手写所有规则
- 能发现与历史BUG相似的代码
- 可以生成简单代码摘要
- 对特定项目可能具有较好的效果

**仍存在的问题**

- 需要大量高质量标签
- 每个任务通常需要单独训练模型
- 很难理解大型PR的整体意图
- 跨文件长距离依赖处理有限
- 解释能力弱
- 从一个项目迁移到另一个项目时性能下降

这个时代可以构建“多个专用模型的集合”，很难形成通用代码审查智能体



### 当前LLM智能体方案

可以设计成以下闭环

```
读取PR
  ↓
理解变更和仓库背景
  ↓
规划审查步骤
  ↓
调用编译器、测试、静态分析和搜索工具
  ↓
读取工具结果
  ↓
重新推理与定位问题
  ↓
生成审查意见
  ↓
人工确认或提交评论
```

1. 感知模块

   收集：

   - PR标题和描述
   - Git差异
   - 修改文件
   - Issue需求
   - 测试结果
   - CI日志
   - 仓库目录结构
   - 相关配置

2. 记忆与知识模块

   保存或检索：

   - 项目编码规范
   - 架构文档
   - 历史审查意见
   - 类似bug
   - API文档

3. 规划模块

   把任务分解为：

   ```
   1. 概括PR目标
   2. 确认关键执行路径
   3. 检查正确性
   4. 检查边界条件
   5. 检查并发和安全风险
   6. 检查测试覆盖
   7. 运行验证工具
   8. 汇总证据
   ```

4. LLM推理模块

   负责：

   - 理解代码意图
   - 关联不同文件
   - 比较实现与需求
   - 解释潜在bug

5. 工具模块

   应包括：

   - 编码器
   - 单元测试和集成测试
   - 代码搜索
   - Git历史查询
   - 沙箱代码执行器

   这里不能只依赖LLM阅读代码后的感觉，工具结果才是重要证据

6. 执行模块

   执行：

   - 拉起PR差异
   - 运行测试
   - 定位失败行
   - 生成最小复现

7. 验证模块

   在发布审查意见前检查：

   - 问题是否能够复现
   - 指向的文件和行号是否正确
   - 是否把代码风格误报为bug
   - 是否泄露敏感信息
   - 置信度是否足够高

8. 人类监督

   推荐分级处理：

   ```
   低风险格式建议 → 可以自动提交
   潜在Bug → 附证据后提交
   高风险安全结论 → 人工确认
   自动修改或合并代码 → 必须额外授权
   ```

### 三个时代的总体对比

| 能力           | 1980年代符号主义 | 2015年深度学习   | 当前LLM智能体                  |
| -------------- | ---------------- | ---------------- | ------------------------------ |
| 代码规则检查   | 强               | 强               | 强，可调用现有工具             |
| 语义概括       | 很弱             | 局部可行         | 较强                           |
| 跨文件理解     | 很困难           | 有限             | 较强但不完全可靠               |
| 需求与实现对照 | 基本不可行       | 很有限           | 可行                           |
| 新任务适应     | 必须增加规则     | 通常重新训练     | 可通过提示、示例和工具适应     |
| 解释审查意见   | 固定模板         | 较弱             | 自然语言解释较强               |
| 运行工具验证   | 固定流程         | 可外接           | 可动态规划和调用               |
| 主要风险       | 规则遗漏与误报   | 数据偏差、泛化差 | 幻觉、上下文遗漏、错误工具调用 |

技术演进使这个任务从“几乎不可能”变为“可行”的根本原因是：

1. 符号主义提供了可靠的形式化检查工具；
2. 深度学习让系统可以从历史代码中学习模式；
3. 预训练让模型获得了通用代码和语言知识；
4. LLM让需求、代码和自然语言审查意见可以统一处理；
5. 记忆、规划和工具调用使模型从“只会生成文本”变成“能够采取行动并获取反馈”的智能体；
6. 神经模型与确定性工具结合，兼顾了灵活理解和可验证执行。

最终，真正可靠的代码审查助手并不是“让LLM看一遍代码”，而是：

$ \text{可靠审查} = \text{LLM语义理解} + \text{静态分析} + \text{测试执行} + \text{项目知识} + \text{证据验证} + \text{人类监督} $
